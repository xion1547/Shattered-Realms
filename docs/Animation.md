## Part 1 — What An Animation Is — Three Layers, One Of Them Not Yours

**Status:** SETTLED, verified 2026-08-16.

Three separate things wear the word "animation." Conflating them produced most
of the confusion this document records.

| Layer | What it is | Where it lives | Who touches it |
|---|---|---|---|
| **The asset** | Keyframes and per-joint CFrames | **Roblox's cloud**, not your game | Author in Studio, upload, read-only thereafter |
| **The id** | `"rbxassetid://123456789"` | A Lua table in your repo | You, freely |
| **The track** | `AnimationTrack` — the live playback handle | Memory, per rig, per peer | Created at runtime by `Animator:LoadAnimation` |

**Nothing about an animation ships in your game.** There is no file in the
repo, nothing under `ServerStorage`, nothing to replicate. Your game holds a
number; the peer that plays it fetches the data from Roblox's CDN.

### 1.1 — Vocabulary, because none of this is obvious

| Term | Meaning |
|---|---|
| **Animator** | An object inside a `Humanoid` that plays animations on a rig. One per rig |
| **`Animation` (the Instance)** | A nearly-empty object whose only meaningful property is `AnimationId`. A pointer, not content |
| **`AnimationTrack`** | What `Animator:LoadAnimation(animation)` returns. The handle for `:Play()`, `:Stop()`, `:AdjustSpeed()` |
| **`AnimationPriority`** | Which animation wins when two play at once. Set at author time |
| **Marker** | A named tag on a keyframe. Fires `GetMarkerReachedSignal` during playback |
| **Manifest** | A plain Lua table mapping a name you chose to an id Roblox chose |

### 1.2 — There IS a file layer, and it is a dead end

Before upload an animation is a real Instance tree — `KeyframeSequence` →
`Keyframe` (each with a `Time`) → `Pose` (each with a `CFrame`). It is
serialisable. It can sit in the repo as `.rbxm`.

**And it cannot be played.** `KeyframeSequenceProvider:RegisterKeyframeSequence`
and its successor `AnimationClipProvider:RegisterAnimationClip` both document:

> "The asset ID generated by this function is temporary and cannot be used
> outside of Studio."

Re-verified 2026-08-16 while looking specifically for a change: the
restriction carried over unchanged when `KeyframeSequenceProvider` was
deprecated. The [feature request](https://devforum.roblox.com/t/create-animations-from-keyframesequences-in-live-games/2222384)
for exactly this has been open since March 2023 with no staff reply.

**The upload is not a packaging step that could be skipped. It is the only way
to obtain an id an `Animator` accepts.** `AssetPipeline.md` Part 4 carries the
same finding for meshes.

### 1.3 — What can be read back at runtime

`AnimationClipProvider:GetAnimationClipAsync(assetId)` downloads keyframe data
in a live game, **on the server or the client**. It yields, it can fail, it
must be `pcall`ed, and developers report it being slow under load.

Boot-time or offline only. Never a per-swing dependency. See Part 10.

## Part 2 — What An Animation Contains — And What It Does Not

**Status:** SETTLED. This Part is the answer to a question asked five times.

The proposal that kept returning was: *move animations server-side, and then
the server has trajectory, damage, power — everything.*

**It has none of those.** The complete contents of an animation:

```
KeyframeSequence
├── Priority
├── Loop
└── Keyframe (Time = 0.25)
    ├── Pose "RightUpperArm"
    │   ├── CFrame              ← a rotation
    │   ├── Weight
    │   └── EasingStyle / EasingDirection
    └── KeyframeMarker "impact"
        └── Value (a string)
```

Joint rotations, and when they happen. **No damage. No power. No trajectory.
No range. No cooldown. No hitbox. No cost.**

The only extensible field is `KeyframeMarker.Value` — and anything put there
is data *you* authored, which belongs in the skill definition where the server
already reads it without a webcall.

**So there is nothing in an animation to be authoritative about.** If they
carried damage and reach, holding them server-side would be non-negotiable.
They carry bone angles. Part 12 traces where authority actually lives.

## Part 3 — Who Plays What — And Why Every Client Always Sees It

**Status:** SETTLED, from the
[Animator documentation](https://create.roblox.com/docs/reference/engine/classes/Animator#LoadAnimation).

| Animator location | Who must start it | Result |
|---|---|---|
| Inside a **player's own character** | That player's **client** | Replicates to the server and every other client, free |
| **Not** a player character (dummies, bosses) | The **server** | Replicates to all clients |
| Created by a LocalScript at runtime | — | Never replicates at all |

This is the same network-ownership rule as position streaming: the client owns
its character, so Roblox trusts it to drive its own limbs.

### 3.1 — "Server-animated" does not mean clients cannot see it

**This wording caused confusion twice and is corrected here permanently.**

Every part in `Workspace` replicates to every client — that is the default,
and only `ServerStorage` and `ServerScriptService` are withheld
(`AssetPipeline.md` Part 3). The boss Model exists in the server's DataModel
**and in every client's**, and everyone renders the animation.

The table above is about **which peer calls `:Play()`**, and nothing else. The
real sequence when the server animates a boss:

```
1. Server calls Animator:LoadAnimation(anim):Play()
2. Server fetches the keyframe data from Roblox's CDN
3. Server's Animator runs — it is genuinely playing
4. Roblox replicates the PLAYBACK STATE (which track, time position, speed)
5. Each client's Animator plays the same animation locally, in sync
6. Each client also fetches the keyframe data from the CDN
```

The animation is playing in **seven places at once** in a six-player session,
each having independently fetched the same asset. Nobody is authorising
anybody — the server plays it, and Roblox tells every client to play it too.

It is exactly like moving a part: the server sets a CFrame, every client sees
it move, and nobody asks how.

### 3.2 — Why the rule exists at all

Not for visibility. For initiation:

- A player's own character **must** be started client-side — server-started
  would cost a full round trip to do something the client can do this frame.
- An NPC **must** be started server-side — client-started would not replicate
  at all, so five of six players would see a statue.

## Part 4 — Asset Ownership — The Decision Before The First Upload

**Status:** SETTLED as a rule. **The decision itself is UNMADE and blocks
work.**

**An animation asset must be owned by the same account or group that owns the
experience, or it fails to load with a permission error.**

This is the most expensive mistake available in this document, because it is
invisible until it is not and the remedy is re-uploading everything.

- Uploading under a personal account and later moving the game to a group
  **breaks every animation at once.**
- Group role permissions are [documented as not covering animations
  properly](https://devforum.roblox.com/t/asset-permissions-in-the-new-creator-group-roles-do-not-work-with-animations/3291942),
  so "fix it with permissions later" is not reliably available.

**Decide the owner before the first upload.** If Shattered Realms will ever be
group-owned, create the group now and upload everything under it from day one.

**The same rule governs meshes.** One decision covers both; see
`AssetPipeline.md` Part 9.

### 4.1 — Naming convention, decided up front

The Roblox asset name is not load-bearing — the id is — but it is the only
thing visible in a list of two hundred uploads.

```
SR_<CLASS>_<ACTION>_<VARIANT>

SR_WARRIOR_SWING_1
SR_WARRIOR_SWING_2
SR_WARRIOR_PARRY
SR_BOSS_GOLEM_SLAM
```

The manifest key is the asset name minus `SR_`, so one grep finds the manifest
row, the skill definition, and the upload.

## Part 5 — The Manifest — Content Layer, One Row Per Animation

**Status:** PROVISIONAL. UNBUILT.

```lua
-- src/shared/definitions/AnimationManifest.luau
return {
    WARRIOR_SWING_1 = {
        assetId  = "rbxassetid://123456789",
        priority = Enum.AnimationPriority.Action,
        fadeTime = 0.1,
        loadFor  = { "WARRIOR" },
    },
}
```

### 5.1 — Why `src/shared/` and not `serverShared/`

The three-tree test (`Architecture-Reference.md` Part 13) asks: *does the
client genuinely execute this?* The client is the peer that plays a player's
animations, so yes.

The disclosure cost is nil — asset ids are readable off any character's
Animator anyway. This is one of the few additions to `ReplicatedStorage` that
costs nothing.

### 5.2 — What must NOT be in this table

`activeWindow`, damage, range, cooldown, or any number the server resolves
with. Those live in the skill definition, server-side. Part 9 explains why
putting them here would *manufacture* the drift problem it looks like it
solves.

### 5.3 — Why `loadFor` exists

The manifest can list every animation in the game at negligible cost — it is a
table of strings. The real cost is `Animator:LoadAnimation`, which builds an
`AnimationTrack` per animation per rig and holds it in memory. `loadFor`
declares which loadouts need it, so tracks are built per loadout rather than
per manifest. See Part 7.2.

## Part 6 — The Pipeline, Step By Step

**Status:** PROVISIONAL.

### Step 1 — Author

Build in Studio's Animation Editor against a rig matching the one it will play
on. **R15 and R6 are not interchangeable** — see Part 17.

### Step 2 — Set priority at author time

`AnimationPriority` decides what wins when two animations play at once. Set it
in the editor, so a manifest override becomes an exception rather than the
norm.

| Priority | For |
|---|---|
| `Core` | Roblox's default idle/walk |
| `Idle`, `Movement` | Locomotion you replace |
| `Action` | Standard attacks |
| `Action2`–`Action4` | Layered on top: ultimates, reactions, cinematics |

**A swing authored at `Core` is silently overpowered by the default walk cycle
and appears not to play.** It looks identical to "the asset failed to load,"
and it is a common first bug.

### Step 3 — Upload

Under the owner decided in Part 4. Record the id.

### Step 4 — Register in the manifest

One row (Part 5). **This is the only code edit a new animation requires.**

### Step 5 — Reference it from a skill

The skill definition names a **manifest key**, never an asset id. Putting a
cloud identifier in gameplay data defeats the manifest and couples the skill
table to Roblox's numbering.

### Step 6 — Boot validation

Part 10. At minimum: every `animationId` a skill names exists in the manifest,
and every manifest row's asset actually loads.

### Step 7 — Play

Client for the player, server for everything else (Part 3).

## Part 7 — Playback — The Client Module

**Status:** PROVISIONAL. UNBUILT.

```
src/shared/definitions/AnimationManifest.luau    ids, priority, fade, loadFor
src/…/client/playback/Rig.luau                   play(name) -> AnimationTrack?
```

> **BUILT 2026-08-23 as `Rig.luau`, not `Animation.luau`.** Two reasons, both
> biting at a require site: `Animation` **is a Roblox class** — the near-empty
> Instance this module instantiates — and Part 1 already warns that three
> things wear that word. What it owns is one BODY's tracks, and the body is
> what invalidates them.
>
> **And it is flagged for replacement.** It is hardcoded to `LocalPlayer`,
> `Humanoid` and `CharacterAdded`, so it cannot animate a sword prop, a door or
> a boss — all of which are rigs. The Conductor is the single door for
> client-side animation (`Timeline.md` Part 12), and it takes an injected
> clip player rather than requiring this. The parts worth salvaging: one
> rebuild path for respawn and loadout, refusing to *create* an `Animator`, and
> the `Length`-reads-0 check.

It is the only thing that touches an `Animator`. It never decides *whether* to
play — InputSystem and Presenters decide; playback renders. This is the
PLAYBACK concern from `Client-Architecture.md`.

### 7.1 — Cache the track, not the Animation instance

`LoadAnimation` is not free, and the first play of an asset stalls while
Roblox fetches it. Build tracks at spawn, keep them.

`ContentProvider:PreloadAsync` takes **Instances, not id strings** — you pass
the `Animation` objects. It [helps but does not fully
eliminate](https://devforum.roblox.com/t/animation-preloading/2765869)
first-play delay, which is a second reason to pre-build tracks rather than
rely on it.

### 7.2 — Load tracks per loadout, not per manifest

```
Manifest lists everything.
Tracks are built only for the player's current class and weapon.
Loadout change rebuilds the set.
```

### 7.3 — Rebind on CharacterAdded, always

Death produces a new rig with a new `Animator`. **Every cached track from the
old body is dead.** The same code path that rebuilds on loadout change
rebuilds on respawn — if these are two paths, one of them will rot.

### 7.4 — Track loading is also the load-failure check

`AnimationTrack.Length` [returns `0` until the asset has fully
loaded](https://create.roblox.com/docs/reference/engine/classes/AnimationTrack).
That makes it both the duration source and the "did this asset resolve" test —
which is the only symptom the Part 4 ownership trap produces.

Check it once after building a loadout's tracks, aggregate, fail loudly. **A
character that silently does not animate is the failure this prevents**, and
it is the likeliest failure in the first month.

## Part 8 — Plays Versus Calculated — Two Timelines That Never Touch

**Status:** SETTLED as a principle.

```
CLIENT (visual)                     SERVER (truth)
──────────────                      ──────────────
t=0.000  click
         track:Play()      ─┐
t=0.016  frame 1            │  event in flight
t=0.033  frame 2            │
t=0.050  frame 3            ├──→  t=0.050  event arrives
                            │             at = t − 0.100  (rewind)
t=0.066  frame 4            │             overlap resolved, 3 hits
                            │             (microseconds, not 120ms)
t=0.083  frame 5            │
t=0.500  animation ends    ─┘
```

Two clocks. Two independent processes. The animation finishes ~450ms after the
server already decided the outcome, and that is correct.

**What connects them: nothing mechanical.** Only authoring intent — you tune
`activeWindow` to roughly match the moment the sword looks like it lands. If
they drift, the swing feels slightly off. **Nothing breaks and nothing becomes
exploitable**, because the server never read the animation.

**That is the payoff of the whole design: the coupling is aesthetic, not
functional.** Part 11 is what protects it.

## Part 9 — `activeWindow` — What It Means And Why It Is Not A Mirror

**Status:** SETTLED. `activeWindow` and `samples` are owned by
`HitDetection.md` §8; this Part explains their relationship to animation and
does not restate their mechanics.

### 9.1 — What a hit test actually needs

A hit is one question: *is this body inside this attack's shape?* That is
`Overlap` — pure math, no time.

But bodies move, so the question is incomplete. The real question is: *is this
body inside this shape **at moment T**?* Every hit test needs a shape **and a
moment**.

`activeWindow` is entirely about the second one. It has nothing to do with
measuring overlap.

### 9.2 — Why one moment is not enough

An enemy sprinting across the front of a 12-stud arc:

| moment | enemy x | inside the arc? |
|---|---|---|
| t = 0.00 | −14 | NO |
| t = 0.06 | −8 | YES |
| t = 0.12 | −2 | YES |

Test once at `t = 0.00` → **miss**. On screen the sword swept through them.
The netcode is correct and the game feels broken.

`activeWindow = 0.12` says the blade is dangerous for 120ms; `samples = 3`
says check three times across it. Results are unioned and **deduplicated by
entity** — three samples catching one enemy is one hit, one damage roll.

**So `activeWindow` does not measure whether something is hit.** `Overlap`
measures that. `activeWindow` decides **how many chances the overlap test gets
and at which moments.**

### 9.3 — Why the whole window resolves instantly

The server does not set a 120ms timer and poll. Every entity records its pose
30 times a second into a ring buffer, so "where was this enemy at `at + 0.06`"
is a **lookup**, interpolated between the two nearest samples.

**The ring buffer is a time machine, and `activeWindow` is what makes a swing
use it more than once.**

### 9.4 — A behaviour nobody had written down

`at` is already in the past — `viewTimeFor` rewinds by roughly
(ping × 2 + 0.1s). Samples then walk **forward** from `at`:

```
activeWindow = 0.12, rewind = 0.10

at + 0.00  = now − 0.10   ← history lookup
at + 0.06  = now − 0.04   ← history lookup
at + 0.12  = now + 0.02   ← THE FUTURE
```

`SpatialComponent:poseAt` clamps a future timestamp to the newest sample —
deliberately, per its own comment. **So a window longer than the rewind stops
being rewound partway through and quietly becomes a live position read.**

Not a bug. Not documented anywhere before now. Worth knowing before setting a
first non-zero window.

### 9.5 — The drift problem, correctly framed

> *"I'm supposed to have mirrored numbers, and they live on different systems
> (one client, one server). If they ever skew, we'd have unexpected
> behaviour."*

Real problem. **Mis-stated in one important way**, and the mis-statement leads
somewhere harmful.

**It is not a client/server problem.** There is exactly one gameplay-timing
number and it is server-only:

| Thing | Where | Read by |
|---|---|---|
| `activeWindow`, `samples` | `HitVolume` on the skill definition, server | `TargetResolution` |
| Visual timing | The animation asset, Roblox's cloud | Whichever peer plays it |
| A copy on the client | **Does not exist and must not be created** | — |

**The trap:** framing this as client/server drift makes *"put `activeWindow`
in `src/shared/` so both sides agree"* look like the fix. That broadcasts
every hitbox timing in the game to every client **and creates the second copy
that did not previously exist.** The framing error manufactures the bug.

**The real axis is code ↔ art:** one number in the repo, one asset in the
cloud, no automatic relationship.

### 9.6 — This problem does not exist yet, and is opt-in

`BASIC_SWING` is `activeWindow = 0`, `samples = 1`. `CombatService:OnAttack`
resolves the instant the event arrives. **No window, nothing to drift.**

The problem is *created* by setting `activeWindow` non-zero. So the first
decision is not "how do I sync" but:

> **Which skills earn a timed window at all?**

A swing that resolves on click has zero drift surface, permanently. A parry
with a 200ms window has a real one. Most MapleStory-shaped attacks are the
former.

**Default to `activeWindow = 0`.** Reach for a window when a skill needs one —
a sweep long enough for a mob to run through, a parry, a multi-hit flurry —
never because attacks "should" have windups.

### 9.8 — STRETCH THE ANIMATION TO THE NUMBER, do not match them by hand

**Status:** DESIGNED, UNBUILT. This supersedes the "author them to match"
posture the rest of Part 9 assumes, and it is a better answer than the
validation ladder it partly replaces.

Everything above treats code↔art drift as something to *detect* — Level 2
catches a missing asset, Level 3 bakes timing out of markers. Both accept that
two numbers exist and try to keep them honest.

**There is a third option: make one of them not exist.**

`AnimationTrack` plays at any speed. So the client does not need an animation
whose length already matches the attack — it needs one it can *stretch*:

```
attack duration, resolved from skill + weapon    0.30s   (a dagger)
the animation's own length                       0.50s
        → play it at 0.50 / 0.30 = 1.67x speed
```

**They cannot drift, for any weapon, ever**, because the animation is fitted to
the number rather than authored to guess it. One swing animation serves a slow
greatsword and a fast dagger, and neither needs re-authoring.

**It does not break facts-not-commands** (Part 11). A duration is a *fact about
the attack* — the same category as the server timestamp the payload already
carries. The client still decides which animation to play; it is now also told
how long the thing it is depicting actually took.

**What it does NOT fix, and this is the boundary:** an animation player can
stretch a clip in **time**, not in **angle**. A swing that traverses 140° on
screen traverses 140° at any playback speed. That is exactly why
`HitDetection.md` §8.4 permits a weapon to modify `activeWindow` and forbids it
from touching `sweep` — one is stretchable and the other is baked into the
art.

`HitDetection.md` §8.4 owns the composition rules; this section owns what
playback does with the result.

### 9.7 — What can and cannot be derived from an animation

| Number | Derivable? |
|---|---|
| `activeWindow`, windup duration | **Yes** — via markers, Part 10 Level 3 |
| Total animation length | **Yes** — `AnimationTrack.Length` |
| `radius`, `angle`, `size`, `length` | **No.** There is no "measure the blade" export |
| `maxTargets`, `hitsPerTarget` | **No.** Pure design values with no visual counterpart |

Only timing has an asset-side source of truth. Everything geometric stays
hand-tuned against the visual, in every engine.

## Part 10 — The Validation Ladder

**Status:** Level 1 SETTLED and in use by default. Levels 2 and 3 UNBUILT.

Three levels of rigour against code↔art drift. Climb only as skills earn it.

### Level 1 — Hand-authored, tuned by eye

**This is the default and it is not "hoping."** A designer sets `activeWindow`
watching the animation and re-tunes when either side changes. Drift is real
but bounded, because "does this still feel right" is checked whenever either
side is touched — the same discipline as tuning damage numbers. Every shipped
game does this for most attacks.

### Level 2 — Boot validation of existence, not timing

The same instinct as `verifySampleRate` and the
`HISTORY_SECONDS >= MAX_REWIND` boot assert: **make staleness impossible to
ship quietly.** One aggregated failure, not a `warn` per row.

```
every skill's animationId names a real manifest row
every manifest row has a non-empty assetId
every loaded track reports Length > 0        (asset resolved, Part 7.4)
every manifest row is referenced by something (dead-row warning)
```

**Deliberately NOT checked here: timing.** An earlier draft proposed warning
when `activeWindow` was "wildly off from the animation's length." That is not
a meaningful comparison — a 1.2s swing with a 0.12s window is *correct*. The
window is a slice, not a measure. Timing validation needs marker data, which
is Level 3.

**The server can run this.** `GetAnimationClipAsync` works server-side
(Part 1.3), so boot-time verification that every referenced animation exists
and loads is available even though the data cannot be held.

### Level 3 — Markers as the source of truth

The equivalent of Unreal's AnimNotify and Unity's Animation Events. Place
named markers (`ACTIVE_START`, `ACTIVE_END`) on the timeline, then read them:

```
GetAnimationClipAsync(assetId)
  → for each Keyframe
      → for each marker in keyframe:GetMarkers()
          → record marker.Name at keyframe.Time
```

**Markers carry no `Time` of their own** — the time comes from the parent
`Keyframe`. `Keyframe:GetMarkers()` returns an array of `KeyframeMarker`.

Now `activeWindow` is *generated* from the asset rather than duplicated beside
it, and moving the impact frame moves both timings at once.

**Two hard constraints:**

1. **Never at runtime, never per-swing.** `GetAnimationClipAsync` yields and
   can fail. It belongs in an **offline content-build step** writing a
   checked-in file, with boot validating that the file still matches. A
   boot-time webcall per animation per server start is the wrong shape.
2. **Timing only.** Reach, radius and angle are unaffected (Part 9.7).

**Do not build this until a specific skill needs frame-accurate timing.**
Building the marker pipeline for every skill pays a real cost for skills that
resolve instantly and have no timing to be accurate about.

### Which level applies

| Situation | Level |
|---|---|
| `activeWindow = 0` | 1 — nothing to drift |
| Any skill with a non-zero window | 1, plus 2 once real skills exist |
| A parry, or a multi-hit whose beats must land on the visual | 3, for that skill only |

## Part 11 — Markers Never Drive Damage

**Status:** SETTLED. Rejected with reasons, because it will look appealing
again.

Roblox provides `AnimationTrack:GetMarkerReachedSignal("impact")`, which fires
during playback when a named marker is reached. It is the standard tool for
"damage lands on frame 14." **It must not be used that way here.**

**Two independent reasons, either sufficient:**

1. **It is client-side for players.** A player's animation plays on their
   client (Part 3), so the marker fires there. The server never sees it. Every
   published solution ends at "fire a RemoteEvent from the marker" — a client
   telling the server when damage happens. That is exactly what
   `SpatialService`, the ring buffer and the rewind exist to make unnecessary.
   An exploiter skips the animation entirely and fires the remote at will.

2. **It is on the wrong clock.** The marker fires at *client playback time*
   while the rewind is anchored to `GetServerTimeNow()`. Feeding a
   client-clock trigger into a server-clock system is the same family as the
   `receivedAt` trap in `DocDebt.md` — it would not error, it would resolve
   hits against the wrong moment forever.

**Markers are worth using for cosmetics only.** Footstep sounds, weapon
trails, screen shake, dust. Client-side effects where being wrong costs
nothing.

**The rule, stated once:** the hit volume is server math. It never derives
from the animation at runtime. They are authored to match (Part 10), and a
mismatch is silent — the sword visibly passes through and nothing errors.

## Part 12 — Animation Is Not A Security Surface

**Status:** SETTLED.

A recurring instinct is that animations could authorise or validate an attack
— that if the server holds them, it controls what players can do.

**It cannot, and it buys nothing.** A client can already play any animation it
wants on its own character; that is what network ownership means (Part 3). A
client playing a swing is not evidence it swung, and a client *not* playing
one is not evidence it did not.

### 12.1 — Where authority actually lives, and it is already server-side

| Authority question | Answered by | Location |
|---|---|---|
| Does this entity own this skill? | `SkillService:isUnlocked` | server |
| Is it off cooldown? | `SkillService:isReady` | server |
| Is the entity allowed to act? | `StateService` | server |
| What shape does the attack hit? | `HitVolume` on the skill definition | server |
| Who was inside it at the compensated moment? | `SpatialService` + `TargetResolution` | server |
| How much damage? | `DamageResolution` | server |

**A client playing an unauthorised animation accomplishes nothing.** It is a
lie told to its own screen: no damage, no movement, no state change, nothing
another player observes as gameplay. The single exception is hurtbox shape —
Part 13.

### 12.2 — The cancel/reject loop already exists

> *"If they play the animation go for it, but I might send a packet back that
> will rewind your cheat or just call `.cancel` on it."*

That is the built design, not a change to it:

| Step | Where | State |
|---|---|---|
| Client plays optimistically, registers the pending action | `PendingActions:add` | BUILT, with timeout |
| Server disagrees | `EventRouter:reject()` | BUILT |
| Client cancels the track | `EventSender`'s `onResolved` | BUILT, untested end to end |

`Architecture-Reference.md` Part 15 owns the correlation contract and the
explicit-reject carve-out.

## Part 13 — The One Carve-Out — Per-Part Hurtboxes

**Status:** SETTLED as a rule. The hurtbox work itself is UNBUILT and owned by
`HitDetection.md` §7.

`HitDetection.md` anchors a hurtbox to each tracked part of a model, so **where
a body is hittable follows the animation.** Not the animation *data* — the
physical result of playing it. That is a real exception to Part 11's rule, and
it needs a boundary.

**The boundary is network ownership, not entity type:**

> A hurtbox may be anchored to any part whose position the **server**
> controls. Anchoring to a part driven by a *client's* animation lets that
> client reshape its own hittable volume — position validation does not catch
> it, because the position is fine and the **shape** is the lie.

**Why not "players are different from bosses":** that is an entity-type
branch, which `Architecture-Reference.md` Part 2 forbids — *"the engine handles
categories; if it is handling instances, the design is wrong."* It would also
be wrong on the merits, since the same hazard applies to a client-owned pet or
to any NPC whose ownership is handed to a client for performance. Ownership is
a property that can be **read**; entity kind is a category someone has to
remember to check.

**Consequence worth stating loudly:** Part 3's "NPC animations are started by
the server" is no longer a rendering detail. **It is load-bearing for hit
detection.** Moving a boss's animation to the client for performance would
silently make its hurtboxes client-controlled — nothing would error, and the
exploit would be invisible. If that is ever proposed, this paragraph forbids
it.

## Part 14 — Scaling — What The Fortieth Attack Costs

**Status:** SETTLED as the design target.

| Piece | Cost of one more attack |
|---|---|
| Animation asset | Author + upload (art time — unavoidable in any engine) |
| Manifest | 1 row |
| Hit volume | 1 table on the skill definition |
| `CombatService` | **0 lines** |
| `TargetResolution` | **0 lines** |
| Client playback | **0 lines** |
| Networking | **0 lines** |

Two data edits, no code. This is generic engine + declarative configuration

as a name, not as a dependency.

## Part 15 — Rejected Designs

**Status:** SETTLED. Each kept with the test that catches it.

**Ship animations as `.rbxm` KeyframeSequences and play them locally.**
Registered ids are Studio-only (Part 1.2). The data loads; nothing can play
it. Re-verified against `AnimationClipProvider` — restriction unchanged.

**Move animations under `ServerStorage` for authority.** Impossible, and
unnecessary: an animation holds joint rotations and no gameplay data (Part 2).
Authority already lives server-side in six places, none of which read one
(Part 12.1). This proposal returned five times; it is recorded at length for
that reason.

**Server sends "play animation X for Y seconds."** The command shape. Every
new animation becomes a server change and server code fills with cosmetic
knowledge. Facts, not commands — `Client-Architecture.md` PLAYBACK.

**`activeWindow` in `src/shared/` so client and server agree.** There is no
client copy to agree with. Broadcasts every hitbox timing and creates the
duplicate it claims to fix (Part 9.5).

**Damage triggered by `GetMarkerReachedSignal`.** Client-authoritative timing
on a server-authoritative system, on the wrong clock (Part 11).

**`GetAnimationClipAsync` at boot, per animation, per server start.** Yielding
webcall that can fail, paid on every server start. Offline build step instead
(Part 10 Level 3).

**Level 2 validation comparing `activeWindow` to animation length.** Not a
meaningful comparison — the window is a slice of the animation, not a measure
of it (Part 10).

**Lazy-loading manifest rows to save memory.** The manifest is a table of
strings. The cost is `LoadAnimation`; scope that instead (Part 5.3).

**An `AnimationService` on the server.** Animation is a client rendering
concern. `ANIMATION` is deliberately absent from `EventRoutingRegistry`, and
an inbound one is correctly rejected as UNROUTABLE.

**Deriving hurtbox geometry from the animation.** Only *timing* has an
asset-side source of truth (Part 9.7). Reach and angle stay hand-authored.
